# Go lens

These rules add checks for Go code.

Files: `**/*.go`

- `GO-2` `defer resp.Body.Close()` / `defer f.Close()` placed before the `err` check of the call that returned it → check `err` first, then defer. Applies: `defer\s+\w+(\.Body)?\.Close\(\)`. Source: https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/httpresponse (resp is nil when err is non-nil, so the defer panics; staticcheck SA5001)
- `GO-3` An HTTP response body that is not closed on every path (including non-2xx returns) → `defer resp.Body.Close()` right after the error check. Applies: `\.(Do|Get|Post|PostForm|Head)\(`. Source: https://pkg.go.dev/net/http#Client.Do ("If the returned error is nil, the Response will contain a non-nil Body which the user is expected to close"; an unclosed body leaks the connection)
- `GO-4` `context.WithCancel` / `WithTimeout` / `WithDeadline` whose `cancel` is not called on every path → `defer cancel()` on the next line. Applies: `context\.With(Cancel|Timeout|Deadline)`. Source: https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/lostcancel ("Failure to call the cancel function ... leaks the context's resources until the parent is canceled")
- `GO-5` A function that has a `ctx` in scope but calls `context.Background()` / `context.TODO()`, or calls a non-context variant (`http.NewRequest`, `db.Query`, `exec.Command`) → pass the caller's `ctx` (`NewRequestWithContext`, `QueryContext`, `CommandContext`). Applies: `context\.(Background|TODO)\(|http\.NewRequest\(|\.(Query|QueryRow|Exec|Prepare|Begin)\(|exec\.Command\(`. Source: https://pkg.go.dev/context ("pass a Context explicitly to each function that needs it"; a dropped ctx means cancellation and deadlines do not reach the call)
- `GO-6` A `context.Context` stored in a struct field, or not the first parameter → pass it as the first parameter `ctx`. Applies: `context\.Context`. Source: https://pkg.go.dev/context ("Do not store Contexts inside a struct type; instead, pass a Context explicitly ... should be the first parameter, typically named ctx"; https://go.dev/wiki/CodeReviewComments#contexts)
- `GO-7` A `go` statement whose goroutine has no exit path: a blocking send, receive, or loop with no `ctx.Done()` / close / `WaitGroup` owner → say when it stops and who waits for it. Applies: `\bgo\s+(func\b|\w)`. Source: https://go.dev/wiki/CodeReviewComments#goroutine-lifetimes ("make it clear when - or whether - they exit"; a goroutine blocked on a channel is never garbage-collected)
- `GO-8` A send on an unbuffered channel from a goroutine whose receiver can return early (timeout, first error, `select` with `ctx.Done()`) → buffer the channel to the number of senders, or `select` on `ctx.Done()` in the sender. Applies: `make\(chan\b|<-`. Source: https://go.dev/wiki/CodeReviewComments#goroutine-lifetimes (goroutines "can leak by blocking on channel sends or receives")
- `GO-9` `wg.Add(...)` called inside the goroutine it counts → call `Add` before the `go` statement (or `wg.Go` in Go 1.25+). Applies: `\.Add\(|\bgo\s+func`. Source: https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/waitgroup (Wait may return before Add runs; staticcheck SA2000)
- `GO-10` A map, slice, or struct field written by more than one goroutine without a mutex, channel, or `sync/atomic` → name the owner and the lock. Applies: `\bgo\s+(func\b|\w)|sync\.|\[.+\]\s*=`. Source: https://go.dev/doc/faq#atomic_maps (map operations are not atomic; concurrent map writes crash the program; https://go.dev/ref/mem)
- `GO-11` A struct containing `sync.Mutex`, `sync.WaitGroup`, `atomic.*`, or `bytes.Buffer` passed or received by value (value receiver, range copy, assignment) → use a pointer. Applies: `sync\.|atomic\.|func\s*\(\w+\s+\w+\)|range`. Source: https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/copylock ("Locks that are erroneously passed by value"; https://go.dev/wiki/CodeReviewComments#copying)
- `GO-12` A value-receiver method that assigns to a receiver field, or mixed pointer and value receivers on one type → a pointer receiver. Applies: `func\s*\(\w+\s+\*?\w+\)`. Source: https://go.dev/wiki/CodeReviewComments#receiver-type ("If the method needs to mutate the receiver, the receiver must be a pointer"; the write goes to a copy)
- `GO-13` A closure started with `go` or `defer` in a loop that uses the loop variable, in a module whose `go.mod` says `go 1.21` or lower → pass it as an argument or shadow it (`v := v`). Applies: `\bgo\s+func|defer\s+func|t\.Run\(`. Source: https://go.dev/doc/go1.22#language (per-iteration loop variables start at 1.22; before that every closure shares one variable; https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/loopclosure)
- `GO-14` `defer` inside a `for` loop (file close, unlock, cancel) → move the body into a function, or release at the end of each iteration. Applies: `\bdefer\b`. Source: https://staticcheck.dev/docs/checks#SA9001 ("Defers in range loops may not run when you expect them to"; they run at function return, so handles pile up)
- `GO-15` (sharper) `err == ErrX` / `err.(*T)` / `strings.Contains(err.Error(), ...)` on an error that any callee may wrap → `errors.Is` / `errors.As`. Applies: `err\w*\s*[!=]=\s*\w*Err|\.\(\*?\w+Error\)|\.Error\(\)`. Source: https://go.dev/blog/go1.13-errors (after wrapping with `%w`, `==` and type assertions no longer match; use Is and As)
- `GO-16` `fmt.Errorf` that adds context with `%v`/`%s` where callers test the cause, or with `%w` on an error from a dependency you do not want in your API → `%w` to keep the chain, `%v` to hide it on purpose. Applies: `fmt\.Errorf\(`. Source: https://go.dev/blog/go1.13-errors#whether-to-wrap (wrapping makes the wrapped error part of your API; not wrapping breaks `errors.Is` for callers)
- `GO-17` A function whose declared return type is an interface (`error`, `io.Reader`) that returns a typed nil pointer variable → return a literal `nil`. Check only functions with an `error` or interface result. Applies: `\breturn\b`. Source: https://go.dev/doc/faq#nil_error (an interface holding a nil `*T` is not `== nil`, so the caller sees a failure)
- `GO-18` An error that is both logged and returned → do one; the top of the call chain logs. Applies: `log\w*\.\w+\(.*err|\.Error\(`. Source: https://google.github.io/styleguide/go/best-practices#error-logging ("let the caller decide" and avoid duplicate logs for one failure)
- `GO-19` `panic` used for an expected error (bad input, I/O failure, not found) outside `main` / `init` / programmer bugs → return an `error`. Applies: `\bpanic\(`. Source: https://go.dev/wiki/CodeReviewComments#dont-panic ("Don't use panic for normal error handling. Use error and multiple return values")
- `GO-20` `os.Exit` or `log.Fatal*` outside `main` (or in `main` after a `defer` that must run) → return an error to `main`. Applies: `os\.Exit\(|log\.Fatal|\.Fatal(f|ln)?\(`. Source: https://pkg.go.dev/os#Exit ("deferred functions are not run"; so file flushes, unlocks, and temp-file cleanup are skipped)
- `GO-21` A returned sentinel value in place of an error (`-1`, `""`, `nil` meaning "not found") → an extra `ok bool` or `error` result. Applies: `return\s+(-1|""|nil)\b`. Source: https://go.dev/wiki/CodeReviewComments#in-band-errors ("Go's support for multiple return values provides a better solution")
- `GO-23` A goroutine per item over an input of unbounded size → a worker pool or `errgroup.Group.SetLimit`. Applies: `for\b.*range|\bgo\s+func|errgroup`. Source: https://pkg.go.dev/golang.org/x/sync/errgroup#Group.SetLimit ("limits the number of active goroutines in this group"; each goroutine holds memory and file descriptors)
- `GO-24` Map iteration order used for output, hashing, pagination, or test assertions → sort the keys (`slices.Sorted(maps.Keys(m))`). Applies: `range\s+\w+`. Source: https://go.dev/ref/spec#For_range ("The iteration order over maps is not specified and is not guaranteed to be the same from one iteration to the next")
- `GO-25` `t.Fatal`/`t.FailNow`/`t.Skip`/`require.*` called from a goroutine started by the test → report through a channel or `t.Error` and return. Files: `**/*_test.go`. Applies: `\bgo\s+func`. Source: https://staticcheck.dev/docs/checks#SA2002 ("Called testing.T.FailNow or SkipNow in a goroutine, which isn't allowed"; vet testinggoroutine)
- `GO-26` `signal.Notify` on an unbuffered channel → `make(chan os.Signal, 1)`. Applies: `signal\.Notify\(`. Source: https://pkg.go.dev/os/signal#Notify ("Package signal will not block sending to c ... For a channel used for notification of just one signal value, a buffer of size 1 is sufficient"; vet sigchanyzer)
- `GO-27` `json.Unmarshal` / `Decode` / `xml.Unmarshal` into a non-pointer, or a struct field that must decode but is unexported → pass a pointer, export the field. Applies: `(Unmarshal|Decode)\(`. Source: https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/unmarshal (non-pointer targets fail at run time; https://pkg.go.dev/encoding/json#Unmarshal only sets exported fields)
- `GO-28` `time.Tick` in a function that can return, in a module with `go.mod` `go` < 1.23 → `time.NewTicker` with `defer t.Stop()`. Applies: `time\.Tick\(`. Source: https://staticcheck.dev/docs/checks#SA1015 (the ticker cannot be stopped and leaks; Go 1.23 made unreferenced tickers collectable, https://go.dev/doc/go1.23#timer-changes)
- `GO-29` `mu.Lock()` with no `defer mu.Unlock()` and an early `return` or panic-capable call before the explicit unlock → `defer mu.Unlock()`, or an unlock on every path. Applies: `\.(R)?Lock\(\)`. Source: https://staticcheck.dev/docs/checks#SA2003 (deferred Lock right after Lock is a common slip; a missed unlock deadlocks the next caller; Effective Go https://go.dev/doc/effective_go#defer)
- `GO-30` (web) In a module on Go 1.22 or later, a `go func` inside a three-clause `for i := ...; ...; i++` loop that assigns to the loop variable → copy it to a local inside the body; the write still races with the loop's own increment, so per-iteration variables do not fix it. Applies: `\bgo\s+func`. Source: https://github.com/golang/go/issues/66388 (vet proposal for this case after 1.22); https://go.dev/doc/go1.22 (per-iteration loop variables). Confidence: medium.
