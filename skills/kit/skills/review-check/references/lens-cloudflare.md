# Cloudflare lens

These rules add checks for Cloudflare Workers, Durable Objects, and Wrangler config.

Files: `**/*.{ts,tsx,js,mjs}`

- `CF-1` A value that depends on one request (user id, auth, env-derived client, a request-built cache keyed without the user) written to a module-level `let`/`var`, a class static, or `globalThis` → keep it in the handler's scope; isolates serve many requests. Applies: `(?m)(^\s*(let|var)\s|globalThis|static\s+\w+\s*[:=])`. Source: https://developers.cloudflare.com/workers/best-practices/workers-best-practices/#code-patterns ("A variable set during one request is still present during the next ... cross-request data leaks")
- `CF-2` A promise that is neither awaited, returned, nor passed to `ctx.waitUntil()` (including an un-awaited RPC or DO stub call) → await it, or `waitUntil` it if it may finish after the response. Source: https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil ("An async call that is neither awaited nor passed to ctx.waitUntil() can be canceled when the invocation ends"); https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/ (always await RPC calls)
- `CF-3` `ctx.waitUntil()` used for work that must happen (billing, a durable write, a notification, state the user will read), or for work that can take more than 30 s, or inside a Durable Object to keep it alive → a Queue, Workflow, or DO alarm; `waitUntil` is best-effort and cancelled after 30 s. Applies: `waitUntil`. Source: https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil (no completion guarantee; cancelled after 30 s; use Queues for longer work; "Do not use waitUntil() to keep a Durable Object alive")
- `CF-6` `idFromName`/`getByName` called with a constant string, or with a key whose cardinality is tiny, for traffic from all users → key the object by the unit that needs coordination (user, room, document), or shard; one object handles about 1,000 req/s. Applies: `(idFromName|getByName|idFromString|newUniqueId)\s*\(`. Source: https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/ (avoid global singletons); https://developers.cloudflare.com/durable-objects/platform/limits/ (soft limit of 1,000 requests per second per object)
- `CF-8` Long synchronous CPU work in a Durable Object request (parsing or sorting a large payload, a big regex, a full-table loop) or `blockConcurrencyWhile()` outside the constructor or around outbound I/O → move heavy work to a Worker or chunk it; use `blockConcurrencyWhile` only for one-time init; every other request to that object waits. Applies: `(blockConcurrencyWhile|JSON\.parse|\.sort\(|for\s*\(|while\s*\()`. Source: https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/ (input gates block new events while synchronous code runs; blockConcurrencyWhile per request caps throughput near 200 req/s at 5 ms)
- `CF-9` A `ctx.storage.sql.exec()` cursor iterated or read after an `await` → consume it with `.toArray()`/`.one()` before any `await`; a cursor held across an await has no snapshot isolation. Applies: `\.exec\s*[<(]`. Source: https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/ (a cursor held across an await "does not provide a stable snapshot of the query results")
- `CF-11` `setAlarm(t)` called by more than one code path, or unconditionally, where an earlier alarm may already be set → read `getAlarm()` and keep the earliest needed time (and do not replace an overdue alarm with a later one); a DO has one alarm and `setAlarm` replaces it. Applies: `(setAlarm|getAlarm|deleteAlarm)`. Source: https://developers.cloudflare.com/durable-objects/api/alarms/ ("Each Durable Object is able to schedule a single alarm at a time"; setAlarm replaces the existing one)
- `CF-12` An `alarm()` handler that is not idempotent, does not set the next alarm when work remains (or sets it only on the success path), or throws on a permanent error → make each step safe to repeat, reschedule before returning while work remains, catch permanent errors and record them; alarms run at least once and a throw is retried with backoff up to 6 times, then dropped. Applies: `(alarm\s*\(|setAlarm|retryCount|isRetry)`. Source: https://developers.cloudflare.com/durable-objects/api/alarms/ (at-least-once; exponential backoff from 2 s, up to 6 retries); https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/ (make alarm handlers idempotent)
- `CF-13` `setAlarm` in a Durable Object constructor without first checking `getAlarm()`, or an alarm interval of seconds on every object → check before setting; schedule only when there is work, at a coarse interval. Applies: `(constructor|setAlarm)`. Source: https://developers.cloudflare.com/durable-objects/api/alarms/ (the constructor runs before alarm() on wake; setting an alarm there can override the scheduled one); https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/ (do not wake every object on short intervals)
- `CF-14` A Durable Object stub reused after a call on it threw, a retry on an error with `.overloaded`, a retry of a non-idempotent call on `.retryable`, or a retry with no backoff → create a new stub after an exception; retry only idempotent calls with `.retryable`, never `.overloaded`, with exponential backoff (`engineering-standards` R3). Applies: `(stub|idFromName|getByName|retryable|overloaded|catch)`. Source: https://developers.cloudflare.com/durable-objects/best-practices/error-handling/ (broken stubs fail every later call; do not retry overloaded; retry only idempotent requests)
- `CF-15` Durable Object state kept only in instance fields (a `Map`, counter, or session list) that must survive eviction, restart, or deploy → persist it to storage and treat the field as a cache that the constructor rebuilds. Applies: `this\.\w+\s*(=[^=]|\.(set|push|add|delete)\(|\+\+|--|\+=)`. Source: https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/ (in-memory state is lost on eviction; no shutdown hook; write state incrementally)
- `CF-16` In a Durable Object that serves WebSockets: `ws.accept()` instead of `ctx.acceptWebSocket(ws)`, `setTimeout`/`setInterval` that keeps the object awake, per-connection state kept only in memory, or `serializeAttachment` data that can exceed 16 KiB → the hibernation API, an alarm instead of timers, state in `serializeAttachment` or storage (store a key when large). Applies: `(\.accept\(\)|acceptWebSocket|setInterval|setTimeout|serializeAttachment|WebSocketPair)`. Source: https://developers.cloudflare.com/durable-objects/best-practices/websockets/ (setTimeout/setInterval prevent hibernation; in-memory state resets; attachment max 16,384 bytes)
- `CF-18` A Durable Object KV `get`/`put`/`delete` given an array or object of keys that can exceed 128 entries, a stored value or SQL row that can exceed 2 MB, or a SQL statement built to exceed 100 KB → chunk or split the value. Applies: `(storage\.(get|put|delete)\s*\(|sql\.exec|INSERT|VALUES)`. Source: https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/ (put up to 128 pairs; get/delete up to 128 keys); https://developers.cloudflare.com/durable-objects/platform/limits/ (2 MB row/value; 100 KB statement)
- `CF-19` Durable Object schema creation or migration run lazily in a request handler, or in the constructor outside `blockConcurrencyWhile` when it awaits → run it in the constructor inside `ctx.blockConcurrencyWhile()`, idempotent (`IF NOT EXISTS`, a stored schema version). Applies: `(?i)(CREATE\s+(TABLE|INDEX)|ALTER\s+TABLE|migrat|schema_?version)`. Source: https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/ (initialize in the constructor with blockConcurrencyWhile so the schema is ready before requests)
- `CF-20` A Durable Object class added, renamed, removed, or switched between key-value and SQLite storage in code without the matching lifecycle declaration in the Wrangler config (a migration entry or an `exports` tombstone) → declare it; storage backend cannot be converted in place. Files: `**/wrangler.{toml,json,jsonc}`. Applies: `(?i)(durable_objects|migrations|new_sqlite_classes|new_classes|renamed_classes|deleted_classes|exports|class_name)`. Source: https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/ (removed class without a tombstone is an error; backends are immutable once provisioned)
- `CF-22` A binding, var, or secret added for one environment in the Wrangler config but read in code that runs in the other environments → declare it in every `env.<name>` block; bindings are not inherited. Files: `**/wrangler.{toml,json,jsonc}`. Source: https://developers.cloudflare.com/workers/best-practices/workers-best-practices/#configuration ("Bindings and vars need to be declared per environment and are not inherited")
- `CF-23` `Math.random()` used for an id, token, nonce, or anything a caller must not guess → `crypto.randomUUID()` or `crypto.getRandomValues()`. Applies: `Math\.random`. Source: https://developers.cloudflare.com/workers/best-practices/workers-best-practices/#security ("Never use Math.random() for anything security-sensitive")
- `CF-24` `ctx.passThroughOnException()` used as the error path → explicit try/catch and an error response. Applies: `passThroughOnException`. Scope: added. Source: https://developers.cloudflare.com/workers/best-practices/workers-best-practices/#security (it hides bugs and makes debugging difficult)
- `CF-25` Durable Object teardown that deletes keys or tables one by one, or calls `deleteAll()` and expects the alarm gone on a compatibility date before 2026-02-24 → `deleteAll()` plus `deleteAlarm()` where the date is older. Applies: `(deleteAll|deleteAlarm|DROP\s+TABLE)`. Source: https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/ (deleteAll removes all storage; deletes alarms only from compatibility date 2026-02-24); https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/
